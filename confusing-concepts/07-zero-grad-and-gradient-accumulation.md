# zero_grad()는 왜 하나, 그리고 gradient accumulation

## 헷갈렸던 점

> `opt.zero_grad()`로 기울기를 지우는데, backward를 하려면 기울기가 있어야 하는 거 아니었나? 여기선 왜 지우나?
> "GPU 메모리가 batch 32까지만 버티는데 batch 128 효과를 내고 싶으면 gradient accumulation"이라는데, batch 128로 하고 싶은 경우가 뭔가? 더 빠르게 하고 싶은 건가? 왜 안 되나, GPU 성능 때문인가?
> 32장씩 4번 하면 개수는 같아도 내부는 다를 텐데, 어떤 관점에서 의미가 있나?

## 결론

- backward의 재료는 **이전 `.grad`가 아니라 이번 forward 때 저장한 중간값(계산 그래프)**이다. `.grad`는 backward의 **결과를 담는 그릇**이고, PyTorch는 여기에 **`+=`로 더한다.** 그래서 매 배치 전에 비워야 한다.
- batch를 키우고 싶은 이유는 **속도가 아니라 기울기의 품질**이다. 더 많은 샘플로 평균 낸 기울기는 노이즈가 적어 학습이 안정적이다. 논문의 하이퍼파라미터를 그대로 재현하려고 할 때도 필요하다.
- 못 키우는 이유는 연산 성능이 아니라 **메모리**다. forward는 backward를 위해 **이미지마다 각 층의 중간값을 저장**해야 해서, batch에 비례해 메모리가 늘어난다.
- 32 × 4 누적은 **batch 128 한 번과 수학적으로 같은 기울기**를 만든다 (실측 차이 2e-8, 부동소수점 오차 수준). 4번 사이에 `step()`을 안 해서 `w`가 그대로이고, 평균의 기울기 = 기울기의 평균이기 때문이다.
- 대가는 **시간**이다. 4번을 순서대로 돌리니 오히려 느리다. 메모리를 시간과 맞바꾸는 기법이다.

## 1. backward에 필요한 것 vs zero_grad가 지우는 것

### 실험

`loss = (w·x - 10)²`, `w = 3`, `x = 2`. 손으로 계산하면 `dloss/dw = 2(wx - 10)·x = -16`.

```
backward 전 w.grad:     None    ← 처음엔 기울기가 아예 없음
1번째 backward 후:      -16.0   ← 정답
zero_grad 없이 2번째:   -32.0   ← -16 + -16 (누적, 틀린 값)
zero_grad 후 3번째:     -16.0   ← 다시 정답
```

- **처음엔 `w.grad`가 `None`인데도 backward가 됐다.** 이전 기울기는 필요 없다.
- backward는 `.grad = 새 기울기`가 아니라 **`.grad += 새 기울기`**.

### "기울기"라는 말이 가리키는 세 가지

```
forward:   x ──(×w)──→ z = wx ──(-10, 제곱)──→ loss
           중간값(x, z)과 "어떤 연산을 했는지"를 기록 (계산 그래프)

backward:  dloss/dz = 2(z - 10)          ← forward 때 저장한 z 사용
           dloss/dw = dloss/dz × x       ← forward 때 저장한 x 사용
           → 결과를 w.grad에 더함
```

| | 무엇인가 | backward에 필요한가 |
|---|---|---|
| **계산 그래프 + 중간값** (각 층의 activation) | forward 때마다 새로 만들고, backward 끝나면 버림 | **필요.** chain rule의 재료 |
| 층 사이로 흐르는 중간 기울기 (`dloss/dz`) | backward 도중 잠깐 계산하고 버림 | backward가 즉석에서 만듦 |
| **파라미터의 `.grad`** (`dj_dw`) | backward의 **최종 결과물** 그릇 | **불필요.** 출력일 뿐 |

"backward하려면 기울기가 있어야 한다"는 두 번째 줄(층 사이로 전달되는 기울기)이고, backward가 그 자리에서 만든다. `zero_grad()`가 지우는 건 세 번째 줄, **이전 배치의 결과물**이다.

### ML 코스 코드와 비교

```python
for i in range(num_iters):
    dj_dw, dj_db = compute_gradient(X, y, w, b)   # 이전 dj_dw 안 씀, 매번 새로 계산
    w = w - alpha * dj_dw
```

```
코스:      dj_dw = 새 기울기                       (= 대입이라 자동 덮어쓰기)
PyTorch:   opt.zero_grad()   → .grad = 0
           loss.backward()   → .grad += 새 기울기   →  결과적으로 .grad = 새 기울기
```

## 2. 왜 batch를 키우고 싶나: 속도가 아니라 기울기 품질

mini-batch 기울기는 **전체 데이터 기울기의 추정치**다. 32장으로 낸 평균보다 128장으로 낸 평균이 진짜 방향에 더 가깝다 (표본이 많을수록 표본 평균이 정확해지는 것과 같다).

```
batch 작음 → 기울기 노이즈 큼 → 경사하강이 이리저리 흔들림
batch 큼   → 기울기 노이즈 작음 → 안정적으로 내려감
```

구체적으로 필요한 상황:
- **논문 재현.** 논문이 "batch 128, lr 1e-4"로 학습했다면 lr은 그 batch 크기에 맞춰 조정된 값이다. batch만 32로 줄이면 같은 lr로도 결과가 달라질 수 있다.
- **큰 모델 학습이 불안정할 때.** diffusion, 고해상도 이미지 모델은 batch가 작으면 loss가 크게 출렁인다.

ML 코스의 batch / mini-batch gradient descent 얘기와 같다. batch가 클수록 한 step이 정확하고, 작을수록 노이즈가 크다.

## 3. 왜 못 키우나: 연산 성능이 아니라 메모리

forward를 하면 backward를 위해 **이미지마다 모든 층의 중간값(activation)을 저장**해야 한다 (1절의 계산 그래프).

```
GPU 메모리 사용량
 = 모델 파라미터            (batch와 무관, 고정)
 + 파라미터의 .grad         (batch와 무관, 고정)
 + optimizer 상태 (Adam)    (batch와 무관, 고정)
 + 각 층의 activation       ← batch 크기에 비례!
```

batch를 4배로 하면 activation 메모리도 4배다. 모델이 크거나 이미지 해상도가 높으면 이미지 한 장의 activation만 해도 크기 때문에, 어느 batch 크기부터 `CUDA out of memory` / MPS 메모리 에러가 난다. GPU가 느려서가 아니라 **한 번에 올려둘 공간이 없는 것**이다.

## 4. 32 × 4가 128 한 번과 같은 이유

```python
opt.zero_grad()
for i in range(4):                       # 32장씩 4번
    loss = loss_fn(model(x[i]), y[i]) / 4
    loss.backward()                      # .grad에 계속 더해짐
opt.step()                               # 128장분 기울기로 한 번 업데이트
```

### 수식

`CrossEntropyLoss`는 배치 평균이다. 128장을 32장 묶음 4개로 나누면:

```
L_128 = (1/128) Σ(128장) ℓ
      = (1/4) × [ (1/32)Σ(묶음1) ℓ + (1/32)Σ(묶음2) ℓ + (1/32)Σ(묶음3) ℓ + (1/32)Σ(묶음4) ℓ ]
      = (1/4) × [ L_묶음1 + L_묶음2 + L_묶음3 + L_묶음4 ]
```

미분은 더하기를 나눠서 해도 되니까:

```
∂L_128/∂w = (1/4)·∂L_묶음1/∂w + (1/4)·∂L_묶음2/∂w + (1/4)·∂L_묶음3/∂w + (1/4)·∂L_묶음4/∂w
```

이게 바로 "`/4`한 loss로 backward 4번, `.grad`에 `+=`"가 하는 일이다. **`+=` 누적 방식이라서 가능하다.**

- `/4`를 하는 이유: 안 하면 평균이 아니라 합이 되어 기울기가 4배로 커진다.
- 4번 사이에 `step()`이 없으니 `w`가 그대로다. 그래서 4개 묶음이 **같은 `w`에서** 기울기를 계산한다. 128장을 한 번에 넣은 것과 조건이 같다.

### 실측

```
batch 128 한번  grad[0,:3]: [-0.08473414, 0.10727814, -0.07148170]
32 x 4 누적     grad[0,:3]: [-0.08473414, 0.10727814, -0.07148170]
최대 차이: 2.2e-08     ← 부동소수점 오차 수준, 사실상 같음
```

### 메모리가 줄어드는 이유

`backward()`가 끝나면 그 묶음의 계산 그래프(activation)는 버려진다. 그래서 동시에 메모리에 있는 activation은 **32장분뿐**이다. `.grad`는 파라미터 크기라서 batch와 무관하게 고정이다.

```
batch 128 한 번:  [activation 128장분] 동시에 → 메모리 부족
32 × 4 누적:      [32장분] → backward, 버림 → [32장분] → backward, 버림 → ...  → step
                   .grad 그릇만 계속 남아서 4번분이 쌓임
```

### ML 코스에서 이미 본 구조

코스에서 직접 짠 `compute_gradient`가 정확히 이 모양이었다:

```python
dj_dw = 0
for i in range(m):                 # 샘플 하나씩
    dj_dw += (f_wb - y[i]) * x[i]  # 누적
dj_dw = dj_dw / m                  # 평균
```

샘플을 하나씩 돌면서 기울기를 **더한 뒤 나눠서 평균** 냈다. gradient accumulation은 이걸 "샘플 하나" 대신 "32장 묶음" 단위로 하는 것이다.

## 5. 그럼 뭐가 다른가 (대가)

| | batch 128 한 번 | 32 × 4 누적 |
|---|---|---|
| 기울기 | 같음 | 같음 |
| 업데이트 횟수 | 1번 | 1번 |
| 메모리 | 128장분 | **32장분** |
| 시간 | 1번에 병렬 처리 | **4번 순서대로 → 더 느림** |
| BatchNorm 통계 | 128장 기준 | 32장 기준 (유일하게 수학적으로 다른 부분) |

- 빨라지는 게 아니다. **메모리를 시간과 맞바꾸는** 기법이다.
- BatchNorm은 forward 안에서 그 묶음(32장)의 평균/분산을 쓰므로 이 부분만 128장과 다르다. 대부분은 무시할 만한 차이다.

## 기억할 것

- backward 재료 = forward의 계산 그래프. `.grad` = 결과 그릇, `+=`로 쌓인다 → 매 step 전에 `zero_grad()`.
- batch를 키우는 목적 = **노이즈 적은 기울기** (속도 아님). 못 키우는 이유 = **activation 메모리** (연산 성능 아님).
- accumulation: `loss / k`로 k번 backward → `step` 1번. 평균의 기울기 = 기울기의 평균이라 결과가 같다.
- 연구 코드에서 `gradient_accumulation_steps`, `accum_iter`가 보이면 이 기법이다. 실효 batch = `batch_size × accumulation_steps`.
